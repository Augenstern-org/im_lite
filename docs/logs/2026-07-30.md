## 概览

## 1. 分层边界定夺与超长帧校验（734e2d1）

### 1.1 `common` / `server` 边界按职责划定

2026-07-29 日志记的遗留是："什么算 common"按遇到问题的先后划，不是按职责划。本次定夺为——**通信双方都要认识的契约与能力归 `src/common/`，只有服务端才需要的机制归 `src/server/`**。

据此三个文件迁位：

| 原位置 | 现位置 |
|---|---|
| `src/server/core/binary_code.h` | `src/common/binary_code.h` |
| `src/server/core/encoder.h` | `src/common/encoder.h` |
| `src/server/core/decoder.h` | `src/common/decoder.h` |

`common/frame_header.h` 原先反向依赖 `server/core/binary_code.h`，这条倒挂的边随之消失。`src/server/core/` 收敛为 `connections.*` 与 `core.*` 两组——epoll 事件循环与连接对象，确实只有服务端需要。

客户端侧同步：`src/client/main.cpp:18` 由 `"server/core/encoder.h"` 改为 `"common/encoder.h"`。

### 1.2 命名空间随目录收敛

上一篇记的"三类类型分属全局 / `types::` / `core::` 三种归属方式"一并定夺：

| 命名空间 | 内容 | 位置 |
|---|---|---|
| 全局 | `Message`、`FrameHeader`、`MessagePack`、`max_message_body_length` | `src/common/` |
| `types::` | `IoStatus`、`ChatTypes`、`MessageTypes`、`Opcode`、`Status`、`is_known_opcode` / `is_known_status` | `src/common/` |
| `codec::` | `Encoder`、`Decoder` | `src/common/` |
| `core::` | `Core`、`Connections` | `src/server/core/` |
| `controller::` | `Controller` | `src/server/controller/` |
| `coordination::` | `User`、`UsersGroup`、`Assembler` | `src/server/coordination/` |

契约类型留在全局命名空间是有意的：它们是三层加客户端的共同词汇，不属于任何一层。

改名波及全部调用点——`core::Opcode` → `types::Opcode`、`core::Encoder` → `codec::Encoder`、`core::Decoder` → `codec::Decoder`，`core.cpp`、`client/main.cpp` 与四个测试文件（`test_binary_code` / `test_decoder` / `test_encoder` / `test_roundtrip`）全线跟随。这部分是纯机械替换，断言语义未变。

`docs/architecture.md` §3.3 同时记下一条命名约定：**不要用 `core` / `codec` / `types` / `controller` / `coordination` 命名类型**。限定名查找（`[basic.lookup.qual]`）在 `::` 之前只考虑命名空间、类型和模板——同名的**类型**会遮蔽命名空间使后续 `core::X` 编译失败，同名的**变量 / 形参 / 数据成员则被忽略**。`src/server/main.cpp:15` 的 `core::Core core(7891, 2);` 与 `:20` 的 `controller::Controller controller;` 属后者，合法但可读性差，新代码不必模仿。

### 1.3 超长帧长度校验落地（编解码两侧）

`IoStatus::FrameTooLong` 此前定义在 `common/io_status.h:14`，但全项目没有任何产出点。本次两侧各补一道：

**解码侧**（`common/decoder.h:44`）——在 `ntohl` 解出 `body_len` 之后、按该长度截取包体之前：

```cpp
body_len = ntohl(body_len);

if (body_len > max_message_body_length) return types::IoStatus::frame_too_long;
if (in_buf.size() - FrameHeader::wire_size < body_len) return types::IoStatus::error;
```

次序有意：上限校验先于"缓冲内剩余字节够不够"的判断，因此对端声明 4 GiB 时返回的是 `frame_too_long` 而非 `error`，绝不用该长度驱动任何分配。`tests/test_decoder.cpp` 的 D8 用例随之从期望 `error` 改为期望 `frame_too_long`，并在注释里钉死这个次序。

**编码侧**（`common/encoder.h:82`）——在序列化完成之后、向 `out_buf` 写入之前：

```cpp
const std::string serialized = body_serializer(rmp.msg_);
if (serialized.size() > max_message_body_length) return types::IoStatus::frame_too_long;
```

这个次序是硬约束：`out_buf` 由调用方按 `wire_size + max_message_body_length` 分配，先写后查等于越界已经发生；比较也必须先于向 `uint32_t` 收窄，否则超过 4 GiB 的体长会被截断成一个看起来合法的小值。

两侧阈值语义一致——`max_message_body_length` 是**帧体字节数，不含 6 字节头**，与 `FrameHeader::body_len_` 同义。

### 1.4 `Encoder` 拆分为 `body_serializer` / `body_writer`

上一条的校验位置要求"帧体长度在任何写入之前就已知"，而原 `body_encoder()` 把序列化与写入捆在一起、返回长度时数据已经落到 `out_buf` 里了。故拆为两个私有函数：

| 函数 | 职责 | 位置 |
|---|---|---|
| `body_serializer(const Message&) -> std::string` | 只序列化，不碰 `out_buf`；非 `noexcept`（`json` 构造可能 `bad_alloc`、`dump()` 遇非法 UTF-8 抛 `type_error.316`） | `encoder.h:45` |
| `body_writer(const std::string&, std::vector<std::byte>&)` | 只写不查，前置条件由 `encode()` 的长度校验保证；`noexcept` | `encoder.h:53` |

`encode()` 的后置条件文档随之扩写：返回 `error` **或 `frame_too_long`** 时 `out_buf` 一字节未动、`rmp.fh_.body_len_` 也不回写——所有可能抛出的操作与长度校验都排在第一次写入之前。

### 1.5 `max_message_body_length`：`static` → `inline`

`common/message.h:13`：

```cpp
-static constexpr std::size_t max_message_body_length = 65530;
+inline constexpr std::size_t max_message_body_length = 65530;
```

`static` 在头文件里给每个翻译单元一份内部链接的副本；该常量现在被 `encoder.h` / `decoder.h` 两个头文件里的函数取用，`inline` 保证全项目只有一个实体。

### 1.6 `Controller::process` 移出头文件

`process` 原本是 `controller.h` 里的内联静态函数。本次移入新启用的 `controller/controller.cpp`，`controller.h` 只留声明；`src/server/CMakeLists.txt` 的 `server` 目标补上该源文件：

```cmake
-add_executable(server main.cpp)
+add_executable(server main.cpp controller/controller.cpp)
```

同时装配器成员换了形态——原先是两个 `coordination::Assembler` 值成员（非静态，而 `process` 是静态，取不到，正是上一篇记的冲突），现改为两个静态 `std::function` 成员加配套 setter：

```cpp
using AckAssembler = std::function<types::IoStatus(/*api*/)>;
using ResAssembler = std::function<types::IoStatus(/*api*/)>;

static AckAssembler ack_assembler_;
static ResAssembler res_assembler_;
```

签名的参数列表仍是空的占位注释——装配器要接什么、返回什么，尚未定义。定义落在 `controller.cpp:10-11`。

`controller.h` 的 `#include <iostream>` 随 `process` 一并移到 `.cpp`，换入 `<functional>`；`coordination/assembler.h` 补入 `common/io_status.h`。

### 1.7 `main.cpp` 包住 `run()`

```cpp
try {
    core.run();
} catch (const std::exception& e) {
    std::cerr << e.what() << std::endl;
}
```

配合 `process` 新增的装配器判空抛出。效果见 §3——异常确实能逸出事件循环被这里接住，但接住之后进程就结束了，连接不会恢复。

### 1.8 文档

`docs/architecture.md` 同步四处：目录树、`common` / `server` 边界的"已定夺"说明与命名空间表、§2.4 收帧流程里的上限常量取值、§7 待定项中"超长帧防护"改记为"长度校验已落地、分帧仍缺"，"`common` 与 `server` 的边界"一项从待定项移入正文。

## 2. 控制层分派雏形（工作区）

### 2.1 出站队列携带目标 fd

`Core::message_handler` 的出参类型变更（`core.h:27-31`）：

```cpp
using message_handler = std::function<void(
    int                       fd,
    const MessagePack&        in,
    std::vector<std::pair<MessagePack, int>>& out_queue
)>;
```

`int` 是该条出站消息的目标 fd。动机是转发——`request` 会产生两条出站消息（转发给对端的 `request`、回给发送方的 `response`），它们的目的地不同，光有消息本身不够。

`core.cpp` 跟随：`send_queue` 换型（`:159`），编码取 `.first`（`:173`）。

**但 fd 目前无人消费**：发送循环（`core.cpp:181-190`）仍然全部写进当前连接的 `conn`，`pair` 的第二元被丢弃。该处已标 TODO（`core.cpp:183`）——核心层现在只能访问正在处理的那个连接，跨 fd 写入的通路还没有。所以这一步是先把类型铺好，行为不变。

### 2.2 按 opcode 分派

`controller.cpp:21-38`，原先无条件回显的 `push_back` 拆成两支：

```cpp
if (rmp.fh_.opcode_ == types::Opcode::ack) {
    MessagePack ack   = rmp;
    ack.msg_.content_ = 0x01;
    out_queue.push_back({ack, fd});
} else if (rmp.fh_.opcode_ == types::Opcode::request) {
    out_queue.push_back({rmp, fd});
    // UserGroup::search(int fd) -> User u
    // UserGroup::search(std::string user_id) -> User u
    // UserGroup::get_user_fd(User user) -> int target_fd
    // out_queue.push_back({msg_pack, target_fd})
}
```

`request` 分支的目标 fd 解析、`UsersGroup` 查表、转发入队都还是注释；`response` 没有分支（服务端不接收 `response`），落到 else 被静默丢弃。

`ack` 分支的 `ack.msg_.content_ = 0x01` 是占位——`content_` 是 `std::string`，这里走的是 `operator=(char)`，结果是长度为 1、内容为字节 `0x01` 的字符串，不是任何约定的应答体。应答帧的实际形态待定。

原先打印 `from_uid_` / `content_` 的两行调试输出一并删除，服务端因此失去了这处观测点（§3 的联调输出可见差别）。

### 2.3 装配器收缩为单个 `ResAssembler`

`AckAssembler` 相关的三处（typedef、静态成员、setter）连同 `request()` / `ack()` 两个空壳私有函数全部注释掉，只留 `ResAssembler`。判空条件随之从 `if (!ack_assembler_ || !res_assembler_)` 收紧为 `if (!res_assembler_)`（`controller.cpp:15`）——但因为两者都没被注册，实际效果不变。

### 2.4 `.gitignore`

新增 `.cache` 与 `.xmake` 两条。前者是 clangd 的索引缓存目录，后者对应 xmake 构建系统（仓库内尚无 `xmake.lua`）。

## 3. 验证

WSL / GCC / CMake 3.28.3，Debug 构建。

**构建与单测**：`cmake --build` 全绿，`ctest` 7/7 全部 Passed（IoStatus / BinaryCode / Message / Encoder / Decoder / RoundTrip / Headers）。头文件迁位与命名空间改名没有留下遗漏——`Headers` 目标会对 `src/` 下每个头文件单独生成翻译单元编译，自足性有兜底。

**端到端联调**：起 `server` 再跑 `client`，三个版本对比如下。

| 版本 | ctest | 服务端行为 | 客户端收到回显 | 服务端存活 |
|---|---|---|---|---|
| `2a71ed5`（远程 HEAD） | 7/7 | 打印 uid / content，回显 | ✅ | ✅ |
| `734e2d1`（本地已提交） | 7/7 | 打印 uid / content，随即抛出 | ❌ | ❌ 退出 |
| 工作区 | 7/7 | 直接抛出（调试打印已删） | ❌ | ❌ 退出 |

`2a71ed5`（即 2026-07-29 日志记录的状态）：


客户端收到完整回显帧：

客户端只打印 `Connected to server`，随后 `recv` 读到 EOF，`len` 不大于 `wire_size`，什么都不输出。

**成因**：`Controller::process` 开头对装配器判空抛 `std::runtime_error`（`controller.cpp:15`），而 `main.cpp:32-34` 的注册调用仍是注释：

```cpp
// 注册装配器
// controller.set_ack_assembler(/* */);
// controller.set_res_assembler(/* */);
```

异常从 `message_handler_` 逸出，穿过 `Core::handle_client` 与 `Core::run`，被 `main.cpp:38` 的 `catch` 接住打印，`main` 随即 `return 0`——进程正常退出，退出码 0。回归自 734e2d1（该版本已含判空抛出与空注册），工作区延续。

这是**装配器接口尚未定义**导致的中间态，不是代码缺陷：`ResAssembler` 的参数列表目前是空的占位注释，无法写出可注册的实现。但需要注意的直接后果是——**在装配器落地之前，服务端一收消息就退出，端到端链路处于不可用状态**，`ctest` 全绿不能代表这一点。

## 已知未收敛点

以下为本次**有意未处理**或**新引入**的问题。

- **端到端链路不可用**：见 §3。装配器接口定义之前无解。可选的临时缓解是把判空改为"未注册则跳过装配、走回显"，但会掩盖真正的未注册错误，未采纳。
- **异常逸出事件循环**：即便装配器注册到位，`main.cpp` 的 `try/catch` 包住的是整个 `run()`——任何一条消息触发的异常都会终结整个事件循环、连带断开所有连接。单连接的错误不应有这样的影响半径，catch 的位置迟早要下沉到 `handle_client` 内部。
- **目标 fd 无人消费**：`std::pair<MessagePack, int>` 的第二元在 `core.cpp:181-190` 被丢弃，全部消息仍写回当前连接。跨 fd 写入需要核心层能按 fd 取到 `Connections` 并驱动其写事件，是转发功能的前置。
- **`response` 被静默丢弃**：`process` 只分派 `ack` 与 `request`，其余 opcode 落到 else 什么都不做，既不入队也不报错。
- **`ack` 应答体是占位**：`content_ = 0x01` 见 §2.2，应答帧形态待定。
- **调试观测点缺失**：`process` 里打印 uid / content 的两行已删，服务端当前对收到的消息没有任何输出。
- **编码缓冲按条分配**（继承自 2026-07-29）：`core.cpp:163-170` 仍为每条出站消息分配 65536 字节并清零。`core.cpp:166` 新增 TODO 提出把超长帧与有效性校验前移到装配器，从而按实际长度分配——方向记下了，未实施。
- **解码状态被丢弃**（继承）：`core.cpp:157` 的 `dst` 取到后从未判定。`frame_too_long` 现在是可达返回值了，这条的紧迫性比上一篇更高——超长帧会被识别出来，然后连同一个未写入的 `MessagePack` 一起交给 handler。
- **回调未判空**（继承）：`core.cpp:160` 直接调用 `message_handler_`。
- **`in.clear()` 位置**（继承）：`core.cpp:185` 仍在发送循环体内。
- **`controller.h` 的传递依赖**：该头文件用了 `types::IoStatus`（`:27`）却不直接包含 `common/io_status.h`，靠 `coordination/assembler.h` 间接引入——而 `Assembler` 本身是空类、并不使用 `IoStatus`。`Headers` 目标查不出这类问题（它只验证头文件能否独立编译，不验证依赖是否直接）。
- **分帧状态机**（继承）：长度校验已落地，但粘包 / 拆包的切分，以及"头部声明超长时如何丢弃后续字节并关闭连接"的连接级处置仍缺。

## 下一步

1. **定义装配器接口**：`ResAssembler` 的参数与返回值——它要从入站 `MessagePack` 和 fd 里拿到什么、产出什么。这是解开 §3 那条阻塞的唯一路径，也决定了 `AckAssembler` 是否需要作为独立类型回归。此前不宜再往 `Controller` 上叠逻辑。

2. **打通跨 fd 写入**：核心层暴露"按 fd 取连接并投递"的能力，让 `std::pair` 的目标 fd 真正生效。此后 `UsersGroup` 的 uid ↔ fd 表才有接入点，`process` 里那几行注释才能落为实现。

3. **核心层错误路径**（继承）：`dst` 判定、`message_handler_` 判空、`in.clear()` 位置三项。`frame_too_long` 已有产出点，`dst` 判定可以先做——这三项属同一处循环的收尾。

4. **异常边界下沉**：把 `try/catch` 从 `main` 移进 `handle_client`，使单连接的异常只影响该连接。

5. **继承项**（自 2026-07-23 / 2026-07-27 / 2026-07-29，仍未实施）：帧校验机制（magic + CRC16）、零拷贝编码路径、分帧状态机、编码缓冲复用。
