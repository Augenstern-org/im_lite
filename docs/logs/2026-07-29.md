# 2026-07-29 - 分层收束与控制器接线

> 三层继承塌缩成一个 `Message`，回显逻辑从 `Core` 交还给 `Controller`。

## 概览

三条线并行推进：**目录分层**——`src/` 平铺改为 `src/server` / `src/client` / `src/common`，头文件搜索路径由单个 `com_lite_base` 目标统一提供；**消息模型塌缩**——`MessageBase` / `RequestMsg` / `ResponseMsg` 三层继承合并为单个 `Message`，`RequestMessagePack` 随之改名 `MessagePack` 并迁入 `common/`；**控制器接线**——`Core` 新增 `message_handler` 回调，"解码 → 处理 → 编码 → 写回"链路从核心层硬编码回显改为经 `Controller::process` 的消息队列。

重构过程中构建一度变红（`test_binary_code` / `test_message` 编译失败），已修复并补上防复发机制——头文件自足性检查纳入 CTest，见 §构建修复。当前 `ctest` 7/7 全绿，且编解码链路首次跨真实 socket 端到端跑通。

## 目录分层与客户端引入（3c8b783）

`src/` 下原本平铺 `core/` `controller/` `coordination/` 与 `main.cpp`——这套布局隐含"整个项目就是服务端"的假设。本次拆为：

```
src/
  server/      core/ controller/ coordination/ main.cpp
  client/      main.cpp
  common/      （彼时仅 io_status.h、message.h）
```

`src/client/main.cpp` 落位：建 TCP 连接到 `127.0.0.1:7891`，发一条硬编码消息，收回显后打印。它存在的意义是给编解码链路一个真实的对端——此前所有验证都在 `tests/` 的内存缓冲里完成，从未跨过 socket。

## 头文件引用规范化（737f5e0）

此前每个 target 各自声明 include 路径，同一个头文件在不同 target 下有不同的写法：`core` 用 `..`、`server` 用三个绝对路径、六个测试目标各自重复一遍 `${CMAKE_SOURCE_DIR}/src/server ${CMAKE_SOURCE_DIR}/include ${CMAKE_SOURCE_DIR}/src`，`/utf-8` 也在每个目标下各写一次。结果是同一份 `encoder.h` 可以写成 `"core/encoder.h"`、`"encoder.h"` 或 `"server/core/encoder.h"`，取决于包含它的文件属于哪个 target。

现改为单一 INTERFACE 目标：

```cmake
add_library(com_lite_base INTERFACE)
target_include_directories(com_lite_base INTERFACE
        ${CMAKE_CURRENT_SOURCE_DIR}/src
        ${CMAKE_CURRENT_SOURCE_DIR}/include
)
```

全项目只剩两个搜索根——`src/`（项目头文件，写成从 `src/` 起的完整路径）与 `include/`（第三方单头文件库 `json.hpp`）。其余目标一律 `target_link_libraries(... com_lite_base)` 继承，不再自行声明路径。所有 `#include` 随之改写为唯一形式：`"server/core/encoder.h"`、`"common/message.h"`。

`tests/CMakeLists.txt` 抽出 `add_com_lite_test(test_name target_name)` 函数，六个测试目标从 46 行样板压到 15 行。

## common/ 层成型（工作区）

`frame_header.h` 与 `message_pack.h` 从 `src/server/core/` 迁至 `src/common/`。触发原因是客户端——`client/main.cpp` 现在直接构造 `FrameHeader` 与 `MessagePack` 再调 `Encoder::encode()`，这两个类型不再是服务端私有。

```cpp
Message r{};
r.from_uid_      = "Remilia";
r.to_uid_        = "Reimu";
// ...
FrameHeader f{};
f.opcode_ = core::Opcode::request;
f.status_ = core::Status::ok;

MessagePack r_msg_pack(f, r);
uint32_t out_len = 0;
core::Encoder::encode(r_msg_pack, bytes, out_len);
```

**遗留问题**：`encoder.h` / `decoder.h` 仍留在 `server/core/` 下，客户端只能写 `#include "server/core/encoder.h"`。编解码器是通信双方共用的能力，与 `frame_header.h` / `message_pack.h` 的性质并无区别——"什么算 common"这条线目前是按遇到问题的先后划的，不是按职责划的。

## 消息模型塌缩（工作区）

原模型是三层继承：

```
MessageBase  { chat_type_, msg_type_, from_uid_, to_uid_, client_msg_id_ }  is_init()
  ├─ RequestMsg  { + content_ }      is_valid()
  └─ ResponseMsg { + server_seq_ }   is_valid()
```

现合并为单一结构体：

```cpp
struct Message {
    types::ChatTypes    chat_type_ = types::ChatTypes::_init_;
    types::MessageTypes msg_type_  = types::MessageTypes::_init_;
    std::string         from_uid_;
    std::string         to_uid_;
    std::string         client_msg_id_;
    std::string         content_;

    bool is_valid() const { /* 六个字段全部非默认 */ }
};
```

`content_` 上提为公共字段，`is_init()` 与 `is_valid()` 合并为单个 `is_valid()`，`ResponseMsg::server_seq_` 一并去掉。旧的三层定义以注释块形式保留在 `message.h:51-76`，其中还有一版按 `char data_[]` 建模的草稿——说明消息体表示方式尚未定案。

连带的重命名：

| 原 | 现 |
|---|---|
| `types::MessageBase` / `types::RequestMsg` | `Message` |
| `core::RequestMessagePack` | `MessagePack` |
| `RequestMessagePack::request_msg_` | `MessagePack::msg_` |

`decoder.h` / `encoder.h` / `core.cpp` / `client/main.cpp` 与三个编解码测试全线跟随改名。测试侧的改动全部是机械替换与格式重排，断言语义与覆盖范围未变（`Encoder` / `Decoder` / `RoundTrip` 三个用例集仍全绿）。

**遗留问题**：命名空间归属现在不一致。`Message` / `FrameHeader` / `MessagePack` 都退到了全局命名空间，`types::` 只剩两个枚举（`ChatTypes` / `MessageTypes`），而 `Opcode` / `Status` 仍在 `core::` 下。同一条链路上的三类类型分属三种归属方式，需要统一定夺。

## 控制器接线（工作区）

### 回调签名

`Core::message_handler` 原型此前是 `std::function<void(int fd, types::RequestMsg)>`——只有入参没有出参，且从未被注册或调用。现改为：

```cpp
using message_handler = std::function<void(
    int                       fd,
    const MessagePack&        in,
    std::vector<MessagePack>& out_queue
)>;

void set_message_handler(message_handler h) { message_handler_ = std::move(h); }
```

出参取 `std::vector<MessagePack>&` 而非单个返回值，是因为一条入站消息可能产生多条出站消息——转发的 `request` 与回给发送方的 `response` 是两条独立的帧。

### 核心层循环

`Core::handle_client()` 中，此前被注释掉的 `Decoder::decode()` 重新启用，硬编码的 `RequestMsg` 构造块全部删除。编码与发送从单条改为遍历 `send_queue`（`core.cpp:155-188`）：

```cpp
MessagePack     rmp;
types::IoStatus dst = Decoder::decode(in, rmp);

std::vector<MessagePack> send_queue;
message_handler_(fd, rmp, send_queue);

// 每条独立编码，再逐条写入写缓冲
```

回显语义随之从核心层移交控制层——`Core` 不再自造消息，只负责搬运。

### Controller 与 Assembler

`Controller::process()` 目前打印 `from_uid_` / `content_` 后把入站包原样 `push_back` 回队列，即行为上仍是回显，但决策点已经在控制层。按 opcode 分派的三条路径（`request` → 转发 + 回 response、`ack` → 应答、`response` → 仅服务端产出）以注释形式占位，`request()` / `ack()` 两个私有静态函数为空壳。

`src/server/coordination/assembler.h` 新建，`class Assembler` 目前是空类。`Controller` 持有 `ack_assembler_` 与 `res_assembler_` 两个成员作为占位——用意是把"从入站包组装出站包"的逻辑从分派逻辑里分出来。

## 构建修复

上述改动一度让构建变红：`test_binary_code` 与 `test_message` 编译失败，`ctest` 6 个用例集里 2 个 Not Run。本节记录修复过程。

### 隐式传递依赖：`binary_code.h` 缺 `<cstdint>`

该文件删掉了 `#include <cstdint>`，却仍用 `std::uint8_t` 作两个 `enum class` 的底层类型。其余翻译单元能过，是因为它们都先经 `common/message.h` → `json.hpp` 间接引入了 `<cstdint>`；`tests/test_binary_code.cpp` 直接包含它，于是 `std::uint8_t` 未声明，两个枚举定义整体报错（头文件内 8 条），并级联出测试文件里的 14 条。

补回 include。同时把两个枚举的底层类型从裸 `uint8_t` 改为 `std::uint8_t`，与文件内两个校验函数的写法统一——`<cstdint>` 只保证 `std::` 限定名可用，全局命名空间的 `::uint8_t` 是 `<stdint.h>` 的保证，混写等于依赖实现的额外好意。

同类问题一并处理（都是"用了某个类型但没包含它的头文件，靠别人间接引入"）：

| 文件 | 补入 | 直接用到的 |
|---|---|---|
| `common/message.h` | `<cstddef>` `<cstdint>` | `std::size_t`、枚举底层类型 |
| `common/frame_header.h` | `<cstddef>` `<cstdint>` | `std::size_t`、`std::uint32_t` |
| `common/message_pack.h` | `<utility>` | `std::move` |
| `server/controller/controller.h` | `<iostream>`、`server/coordination/assembler.h` | `std::cout`、`coordination::Assembler` |

`controller.h` 那两项此前靠 `server/main.cpp` 的包含顺序兜着——`main.cpp` 先包含 `<iostream>` 与 `assembler.h`，`controller.h` 才编得过。补齐之后 `main.cpp` 里的 `assembler.h` 包含已无必要，一并删除。

### 头文件自足性纳入 CTest

上面这类问题的共性是**没有任何机制保证头文件是自足的**——改坏了要等某个特定文件恰好直接包含它才会暴露。新增 `Headers` 目标兜底：

`tests/CMakeLists.txt` 对 `src/` 下每个头文件（当前 13 个）各生成一个翻译单元，内容只有连续两次包含该头文件本身（第二次顺带验证 include guard），全部链进 `test_headers`。断言在编译期完成——头文件若少写自己直接用到的 `#include`，该目标即编不过。

```cmake
file(GLOB_RECURSE COM_LITE_HEADERS CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/src/*.h)
foreach(header IN LISTS COM_LITE_HEADERS)
    file(RELATIVE_PATH COM_LITE_HEADER ${CMAKE_SOURCE_DIR}/src ${header})
    # ... configure_file(header_self_contained.cpp.in ...) 生成 TU
endforeach()
```

用 `GLOB_RECURSE` + `CONFIGURE_DEPENDS` 而非手写清单，是为了新增头文件时自动纳入——清单一旦要手工维护，迟早会漏。

已实测该检查会咬人：临时删掉 `binary_code.h` 的 `<cstdint>` 后，`test_headers` 报 6 条错误。

### `test_message.cpp`

删除 `ResponseMsg` 段落（该类型已随消息模型塌缩去掉），注释里残留的 `MessageBase` 措辞一并订正。

另补四条 `is_valid()` 断言。塌缩之后它是消息合法性的唯一闸门，而此前没有任何用例覆盖它：`content_` 缺失、`chat_type_` 为 `_init_`、`msg_type_` 为 `_init_`、默认构造的 `Message`——四种情形都必须为 false，齐备的消息为 true。

### include 规范收敛

三处相对路径改为从 `src/` 起的完整路径：

| 位置 | 原 | 现 |
|---|---|---|
| `core.cpp:16` | `"../../common/frame_header.h"` | `"common/frame_header.h"` |
| `common/message_pack.h:9` | `"frame_header.h"` | `"common/frame_header.h"` |
| `server/main.cpp:7` | `"coordination/assembler.h"` | 删除（改由 `controller.h` 自行包含） |

至此 `src/` 与 `tests/` 下所有项目内头文件引用均符合 737f5e0 立的规范。规范本身仍无强制手段——引号包含总会先在当前文件目录下找，写相对路径依然编得过。

### `client/main.cpp`

四处修正：

1. **发送长度**：`send()` 传 `out_len` 而非 `bytes.size()`。原先每次把整个缓冲连同尾部零字节发出去；当前服务端能解开只是因为解码器按 `body_len_` 定界、忽略尾部多余字节，一旦启用分帧状态机，这些零字节就会被当作下一帧的开头。
2. **缓冲尺寸**：`512` → `FrameHeader::wire_size + max_message_body_length`。`Encoder::body_encoder()` 直接 `memcpy` 进 `out_buf` 且不做越界检查（注释写明"由上层机制保证资源有效"），512 字节的缓冲在 body 超过 506 字节时就是越界写。当前硬编码的消息远没到这个量级，但缓冲尺寸不该由"目前的消息恰好够短"来担保。
3. **编码结果未检查**：`encode()` 返回 `error` 时 `out_len` 为 0，原先照发不误。现改为报错退出。
4. **打印长度**：用 `recv` 返回的 `len` 而非 `sizeof(buffer)`，跳过帧头后直接 `std::cout.write()` 输出帧体。

## 已知未收敛点

以下均为本次**有意未处理**的问题，按发现位置记录。

- **编码缓冲按条分配**：`core.cpp:166-169` 为 `send_queue` 中每条消息各分配 `max_message_body_length + wire_size`（65536 字节）并清零，与实际帧长无关。同一问题的另一面是 `Encoder` 那个被注释掉的内部缓冲 `buf_`（`encoder.h:28`）——编码器到底该不该持有自己的缓冲，目前没有结论。**决定推迟**：等到确实需要缓冲复用时再一并定夺，不为尚未出现的性能问题先行设计。
- **`Encoder` 不做越界检查**：`body_encoder()` 直接 `memcpy` 进调用方的 `out_buf`，缓冲不够即越界写。当前靠调用方按最大帧长分配来保证，是约定而非机制。与上一条同属"编码器的资源契约"，一并推迟。
- **解码状态被丢弃**：`core.cpp:157` 的 `dst` 取到后从未判定。`decode()` 失败时 `out_rmp` 按设计保持未写状态（见 2026-07-27 日志 §解码器实现第 7 条），于是一个默认构造的 `MessagePack` 会被原样交给 handler。
- **回调未判空**：`core.cpp:160` 直接调用 `message_handler_`，未注册时抛 `std::bad_function_call`。`disconnect_handler_` 的调用处同样如此。
- **`in.clear()` 位置**：`core.cpp:183` 放在发送循环体内，随循环次数重复执行。语义上应在进入编码前一次性消费掉读缓冲。
- **`Controller` 静态与非静态混用**：`process()` 是 `static`（才能直接传给 `set_message_handler`），但 `ack_assembler_` / `res_assembler_` 是非静态成员（`controller.h:25-26`），静态函数取不到——`Assembler` 一旦要用，这个签名就得改。
- **`common` / `server` 边界未定**：`encoder.h` / `decoder.h` 仍在 `server/core/` 下，客户端只能写 `#include "server/core/encoder.h"`；`common/frame_header.h` 又反过来依赖 `server/core/binary_code.h`。方向是反的，但要一次定夺（连同命名空间归属），不适合零敲碎打。

## 下一步

1. **收敛分层边界**：定夺 `encoder.h` / `decoder.h` 的归属（`common/` 还是留在 `server/core/`），以及 `Message` / `FrameHeader` / `MessagePack` / `Opcode` / `Status` 的命名空间归属——目前三类类型分属全局、`types::`、`core::` 三种方式。

2. **Controller 分派与 Assembler**：把 opcode 分派从注释落为实现，`Assembler` 定义出"入站包 → 出站包"的职责边界，并解决 `process()` 的 static / 非静态冲突。此后 `UsersGroup` 才能接进来做真正的转发（当前 `fd` 参数拿到了但没有用）。

3. **核心层错误路径**：`dst` 判定、`message_handler_` 判空、`in.clear()` 位置三项，属于同一处循环的收尾工作，宜一并处理。

4. **继承项**（自 2026-07-23 / 2026-07-27 日志，仍未实施）：帧校验机制（magic + CRC16）、零拷贝编码路径、分帧状态机。其中分帧状态机的优先级因客户端接入而上升——真实 socket 下的粘包 / 半包现在是可复现的，而不再只是理论问题；`IoStatus::FrameTooLong` 至今没有产出点，也要在这一步补上。

5. **编码缓冲**（推迟，无明确触发条件）：见 §已知未收敛点前两条。等到有实际的复用需求或性能证据再动。
