## 1. 装配器落位（a435576）

### 1.1 `Assembler` 从空壳变成具体类

7/29 建的 `coordination::Assembler` 直到 7/30 日志交付时仍是空类——`ResAssembler` 的签名是空的占位注释，无法写出可注册的实现。本次定义了两个成员函数：

```cpp
types::IoStatus assemble_response(const MessagePack& in, std::vector<MessagePack>& out);
types::IoStatus assemble_ack(const MessagePack& in, std::vector<MessagePack>& out);
```

`assemble_response`：把入站 `request` 的 `MessagePack` 复制一份，`opcode` 翻成 `response`、`status` 置为 `ok`，帧体是入站 `Message` 的原样复制——真正该带的服务端消息序号（`server_seq_`）尚未回归，见 TODO.md。

`assemble_ack`：复制入站包，帧体写 `'\x01'`（长度 1、字节 0x01 的字符串），帧头保持入站原样不强制改写。与迁移前 `controller.cpp` 里 `ack.msg_.content_ = 0x01` 的占位逐字节等价。

**装配器不做路由**——签名里没有 fd，也不持有 `UsersGroup`。它只负责把出站 `MessagePack` 装配出来，"送到哪个 fd"由调用方决定。在跨 fd 转发落地之前，出站帧的目标 fd 恒等于入站 fd；因为装配器无法表达 fd，误投在类型上不可发生。这是有意划定的边界（记入 TODO.md §有意缺失/已划定的边界）。

### 1.2 `Controller` 从静态工具重构成实例

此前 `process()` 是 `static`、装配器也是静态 `std::function` 成员——静态函数取不到非静态成员，上一篇记的"静态与非静态混用"冲突正源于此。

重构方案：`Controller` 构造时接收 `coordination::Assembler&`，存为引用成员；`process()` 改为非静态。

```cpp
explicit Controller(coordination::Assembler& assembler) noexcept : assembler_(assembler) {}
void process(int fd, const MessagePack& rmp, std::vector<std::pair<MessagePack, int>>& out_queue);
```

引用成员会隐式删除拷贝赋值——显式 `= delete` 拷贝构造与拷贝赋值，使"不可拷贝"成为写明的意图而非副作用。连带后果：`Controller` 因此既不可拷贝也不可移动（显式 delete 拷贝构造会抑制隐式移动构造），不能放进 `vector`。

`process()` 内部逻辑随之重写：入口校验 `rmp.is_valid()`、按 opcode 分别调用 `assembler_.assemble_response()` / `assembler_.assemble_ack()`、将装配结果逐条 `emplace_back` 进 `out_queue`（目标 fd 恒为入站 fd）。原先注释掉的 `request()` / `ack()` 空壳私有函数连同 `AckAssembler` typedef 一并删除。

### 1.3 `main.cpp` 三组件接线

```cpp
coordination::Assembler assembler;
controller::Controller  controller(assembler);
core::Core core(7891, 2);
```

声明顺序即所有权顺序——`Core` 持有捕获了 `&controller` 的 lambda，反序析构保证 `Core` 先于被捕获对象销毁。`set_message_handler` 的注册从注释恢复为有效调用：

```cpp
core.set_message_handler(
    [&controller](int fd, const MessagePack& in, std::vector<std::pair<MessagePack, int>>& out_queue) {
        controller.process(fd, in, out_queue);
    }
);
```

## 2. 编码缓冲复用（28387f7）

### 2.1 问题

7/29 日志两条已知未收敛点——"编码缓冲按条分配"与"零拷贝编码路径"——前者被指定为后者的前置。`core.cpp:163-170` 为 `send_queue` 中每条消息各分配 `max_message_body_length + wire_size`（65536 字节）并清零，与实际帧长无关。这是 7/27 就已存在的模式，历经多篇日志的「已知未收敛点」而未动。

本次触发条件到了：装配器接好线之后，编码循环是每次 `EPOLLIN` 都要跑的热路径，每轮 65536 × N 的分配不再是可以推迟的"尚未出现的性能问题"。

### 2.2 方案：复用缓冲归调用方持有

**不做** 7/29 考虑的"编码器自持缓冲"——那条路的致命问题是 `Encoder` 得对外返回一个指向内部缓冲的视图（指针/span），而该视图会被下一次 `encode()` **静默失效**：调用方手里是一块随时可能被覆写、甚至因 `realloc` 而悬空的内存，失效时机取决于编码器内部状态，类型上无从表达、编译器也查不出来。

实际方案：

- `Core` 新增 `std::vector<std::byte> encode_buf_` 成员（`core.h:56`），跨消息、跨连接复用；
- `Encoder::encode()` 改为**按需增长** `out_buf`——`if (out_buf.size() < need) out_buf.resize(need)`，只增不减；
- `out_buf` 不再要求调用方预分配，`encode()` 后置条件文档随之扩写：`out_buf.size()` 可能大于 `out_len`，调用方只得读写 `[0, out_len)`，尾部残留的是上一次编码的字节。

缓冲归调用方持有时生命周期归属明确：谁持有谁负责，`out_buf` 活多久由调用方自己的作用域决定，不存在"被下一次 `encode()` 静默失效"的问题。`Encoder` 保持 `static`、保持无状态——这一点与 7/27 以来一直维持的"编解码不对称"设计一致。

### 2.3 `resize` 的位置被前后两侧同时确定

`encoder.h:87-100`，新增一段注释，钉死 `resize` 的精确位置及其两条理由：

**晚于 `frame_too_long` 校验**：出站帧体可能源自入站内容（回显），先分配后校验等于让对端一个声称 65530 的 6 字节帧头就能诱导一次约 64KB 分配——DoS 放大面。

**早于 `rmp.fh_.body_len_` 回写**：`resize` 会抛 `std::bad_alloc`，而 `encode()` 的出错后置条件要求失败路径不回写 `body_len_`。`std::byte` 可平凡复制 → `vector::resize` 提供强异常保证 → 抛出时 `out_buf` 不变；`bad_alloc` 由下面的 `catch (...)` 接住并把 `out_len` 归零。两者合起来，整条出错后置条件继续成立。

这两条理由取代了 7/30 日志（`docs/architecture.md:224`）里已经作废的一条——原来写"必须先校验再写，否则越界"，现在 `encode()` 自己按需增长 `out_buf`，越界不再可能发生。次序硬约束本身**依然是硬约束**，只是现役理由换成了防 DoS 放大与异常安全。

### 2.4 核心层调用点

`core.cpp:162-181`，编码循环从"为每条消息分配 65536 字节 → 编码 → 发送"改为：

```cpp
for (auto& item : send_queue) {
    uint32_t        out_len = 0;
    types::IoStatus est     = codec::Encoder::encode(item.first, encode_buf_, out_len);
    if (est != types::IoStatus::ok) { … }
    types::IoStatus wst = conn.send(reinterpret_cast<const char*>(encode_buf_.data()), out_len);
    if (wst == types::IoStatus::closed || wst == types::IoStatus::error) { … }
}
```

`conn.send()` 会把数据拷进 `write_buf_`，因此编码缓冲的生命周期在 `send()` 返回时即结束，下一轮可以直接覆写。只有 `[0, out_len)` 会被发送，残留字节永不上线。

稳态下 `encode_buf_` 的 `size()` 会收敛到历史最大帧长，此后每次 `encode()` 只在帧长超过当前容量时才 `resize`——零缓冲分配。

### 2.5 `in.clear()` 位置修正

`core.cpp:193-195`：`in.clear()` 从发送循环体内提到循环外，当且仅当 `send_queue` 非空时执行一次。N 次幂等清空 → 1 次，等价搬移。

唯一的差异在发送失败路径——原先 `clear` 排在 `wst` 状态检查之前，失败时也会清空；现在失败直接 `close_client()` + `return`，走不到这里。该差异没有实际后果：`close_client()` 把 fd 推进 `pending_close_`，`drain_pending_close()` 随后 `conns_.erase(fd)` 析构掉整个 `Connections`，`read_buf_` 跟着一起消失——对一个即将被销毁的缓冲区做 `clear()` 是无意义操作。

注释里同时写明了**不可**改成解码后无条件清空的原因：`send_queue` 为空的一种情形是半帧未齐（`decode` 因 `in_buf.size() - wire_size < body_len` 返回 error，控制层随即提前 return），此时「不清空」正是拆包重组赖以工作的机制。无条件清空会丢弃半帧、让连接永久失步。真正的修复要等分帧状态机给出"本次消耗了多少字节"的出参，届时才能按消耗长度精确地从头部截去已消费的字节。

### 2.6 客户端侧

`src/client/main.cpp` 删掉 `bytes.resize(FrameHeader::wire_size + max_message_body_length)` 预分配——`encode()` 现在自己按需增长 `out_buf`，调用方不再负责容量。同文件原有的两行关于"`Encoder` 直接 `memcpy` 不做越界检查"的注释一并删除——该约束已随 `resize` 逻辑失效。

### 2.7 编码器「不做越界检查」→「不检查 `out_buf` 容量」

7/29 日志已知未收敛点中"`Encoder` 不做越界检查、不检查 `out_buf` 容量"的后半句已作废：容量不再是调用方的义务，`encode()` 自己按需增长。前半句（不做内容有效性校验）保持——出站数据由程序自己构造，视为可信；入站数据才是敌意的。编解码不对称是有意的，记入 TODO.md §有意缺失/已划定的边界。

## 4. 核心层错误路径设计锁定（规划，无提交）

本节是一次纯设计工作的记录：`TODO.md` 的「核心层错误路径三连」连同其根因被完整调研并锁定方案，**代码一行未改**。之所以单独成节，是因为过程中推翻了两条此前被当作前提的判断，并发现了两条可被对端直接触发的活缺陷。

### 4.1 被推翻的前提：消耗字节数今天就可得

`TODO.md:47-48`、本文 §2.5、`docs/architecture.md` 与 `codec.md` 都记着同一句话：「`in.clear()` 的真正修复要等分帧状态机给出『本次消耗了多少字节』的出参」。**该前提不成立。**

`decoder.h:62` 写入 `fh.body_len_ = body_len`，`:65` 把 `fh` 落进出参。因此：

```
decode() 返回 ok  ⇒  本帧消耗 == FrameHeader::wire_size + out_rmp.fh_.body_len_
```

该等式**只在 `ok` 时有定义**——其余返回值下出参逐位未动（D20 后置条件，`tests/test_decoder.cpp:278-316`），表达式无意义。但那些路径也不需要消耗量：要么保留字节继续等，要么杀连接。也就是说，"消耗多少"这个信息恰好只在它已经存在的地方被需要。

推论：推进读游标既**不必**等分帧状态机，也**不必**给 `decode` 加出参。真正缺的只有两样，都不是新组件——一个 `while` 循环，和一个「不完整 vs 协议错误」的区分位。

真正需要独立分帧状态机的是**流式增量解析**（不把整帧攒在 `read_buf_` 里就能推进），那是性能议题，与错误路径的正确性无关。

### 4.2 两条活缺陷

均由 `core.cpp:193-195` 的 `if (!send_queue.empty()) in.clear();` 这一个谓词造成——它用「控制层有没有产出响应」去猜「解码器消费了多少字节」，两个方向都猜错。

**(1) 粘包丢帧。** `decoder.h:45` 的守卫是 `in_buf.size() - wire_size < body_len`，缓冲里有多余字节时照样放行，`decode` 正确解出第一帧并忽略尾部；随后 `in.clear()` 把**第二帧连同全部尾随字节整块销毁**。触发条件是对端把两帧写进同一个 TCP 段——`connections.cpp:30-50` 的读循环会一直读到 EAGAIN，合并后必然一次性进 `read_buf_`。至今未暴露的唯一原因是调试客户端只发一帧（`client/main.cpp:63`）。

**(2) 连接楔死 + 读缓冲无界增长。** `send_queue` 为空有四种成因，只有「半帧未齐」该保留字节，另外三种**都已经消耗掉字节**：

| 成因 | 后果 |
|---|---|
| 半帧未齐（`decoder.h:31/:45`） | **正确**，重组机制赖此工作 |
| 协议错误（`decoder.h:37/53/54/57/69`） | 垃圾字节永不清空，每次 EPOLLIN 重复解码同一段，连接永久失步 |
| `frame_too_long`（`decoder.h:44`） | 同上，且永远无法自愈 |
| 帧合法但控制层不产出（`controller.cpp:32-36` 的 `response` opcode） | 该帧滞留缓冲被无限重解码 |

写侧有 `kWriteHighWater = 1MiB`（`connections.cpp:66-68`），**读侧没有对应物**——`kReadSoftCap`（`connections.cpp:36-38`）只终止单次调用的读循环，不限制跨调用增长。持续发送垃圾字节的对端可让 `read_buf_` 单调增长直至 OOM，**全程零日志、零 CPU 异常**（不是空转，只在有新字节时被唤醒）。

这把 `TODO.md:54-56`「`response` 被静默丢弃」的严重性抬高了一档：不是"收到了当没看见"，是"收到就把这条连接卡死"。

### 4.3 锁定的方案

**范围**：分帧推进 + 核心层错误路径三连。明确排除跨 fd 转发（`TODO.md:9-24`）、异常边界下沉（`TODO.md:50-52`）、`init()`/`handle_accept()` 的其余未检查系统调用、以及任何更大的错误处置抽象（`Disposition` / expected 风格）——后者的问题真实但触发条件不足：全项目只有一个解码器、一条消息路径，抽象要成立至少需要第二个消费者。这与仓库既有的「`Channel`/`EventHandler` 抽象等第二种 fd 出现再说」（`TODO.md:155-157`）是同一种纪律。

**接口变更共 2 处，签名净变化为零：**

- `io_status.h` 追加 `incomplete`（放在末尾），`to_string` 补一个 case；
- `decoder.h:31`（帧头未齐）与 `:45`（帧体未齐）的返回值 `error` → `incomplete`，**算术不动**（见 4.5）。其余五个返回 `error` 的站点保持不变。

**显式锁定为"不改"的 4 处**：`decode` 签名（不加 `out_consumed` 出参）、`Connections`（不加 `read_pos_`）、`handle_client` 签名、`message_handler` 别名。

**新增一条契约**：

> 当且仅当 `Decoder::decode` 返回 `IoStatus::ok` 时，本帧消耗 `FrameHeader::wire_size + out_rmp.fh_.body_len_` 字节。其余返回值下该表达式无定义。

### 4.4 重写后的 EPOLLIN 分支

```
while (!in.empty()) {
    dst = decode(in, rmp);
    if (dst == incomplete) break;              // 唯一「保留字节」的出口
    if (dst != ok)        { fatal = true; break; }

    consumed = FrameHeader::wire_size + rmp.fh_.body_len_;
    in.erase(in.begin(), in.begin() + consumed);   // 先推进，再派发
    // ↑ 此行之后，本轮循环再无「既不推进也不终止」的分支

    send_queue.clear();
    if (message_handler_) message_handler_(fd, rmp, send_queue);   // 三连②

    for (auto& item : send_queue) { encode → send; 失败则 fatal = true; break; }
    if (fatal) break;
}
if (fatal || rst == error || (rst == closed && !conn.want_write())) { close_client(fd); return; }
```

**四条承重理由，逐条记下：**

**(a) 循环必须 drain 到 `incomplete`，不设帧数上限。** 全仓无 `EPOLLET`（`update_events` 只组装 `EPOLLIN|EPOLLOUT`），LT 的重新触发看**内核**接收缓冲，而 `on_readable` 已把内核缓冲抽干到 EAGAIN。若只解一帧就退出，用户态 `in` 里的第二个完整帧不会再有 EPOLLIN 来唤醒它——直到对端碰巧再发字节。任何帧数上限都会重新引入这个 stall。唯一的量化闸是 `kReadSoftCap` 64 KiB，与 muduo 的机制 1:1 对应（muduo 同样不设帧数/时间上限，也同样没有输入缓冲高水位）。

**(b) `erase` 必须在 `message_handler_` 之前。** 除了 tokio `Decoder` 的既有契约（缓冲由解码器推进，之后才交给应用），本仓还有一条独立理由：`main.cpp:39-43` 的 `try/catch` 仍包着整个 `run()`（本轮不动）。handler 一旦抛异常，栈会展开出 `handle_client`——游标先推进则毒帧已出局；后推进就是下次再解同一帧、再抛，构成 livelock。muduo 的 `handleRead` 正是在回调前不做任何消费、把游标推进完全委托给应用回调，这也正是"handler 忘了 retrieve → 永久重解码"这一 bug 类的来源。

**(c) `close_client` 从纪律变成控制流性质。** HEAD 上 `handle_client` 有 6 个 `close_client` 调用点（`:136/:144/:171/:178/:199/:204`），各自靠"记得后面写 `return`"维持不重复入队。往这个函数里加循环会让这条手工不变式变得脆弱。锁定方案的处理是：**循环体内 `close_client` 调用点为 0**，所有杀决策只写 `fatal = true; break;`，EPOLLIN 分支收敛成**恰好一个** `close_client(fd); return;`。全函数调用点从 6 降到 3。

**(d) 不加读缓冲上限，因为恒界可推导。** drain 循环退出时 `in` 中只剩一个未完成帧：要么 < 6 字节，要么 `wire_size + k` 且 `k < body_len ≤ 65530`（`decoder.h:44` 已拦）⇒ 残留 ≤ 65535 字节。`on_readable` 每轮 append ≤ 4096 且 `size() >= 65536` 即返回。故 **`read_buf_.size() ≤ 69631 字节（≈68 KiB）恒成立**。承重前提是 `:31` 与 `:44` 必须永远先于 `:45`（见 4.5）。

诚实的余项：慢速对端仍可声明 65530 后永久涓流，把约 68 KiB 挂住不放。`IoStatus::timeout` 至今零产出点、无空闲超时机制。本轮既不引入也不修复这条 slowloris 面。

### 4.5 两条被核实为"已经满足"的前提

调研阶段曾担心两处，实测**HEAD 上均已满足**，只需把它们升格为注释里的承重约束：

- **`frame_too_long` 检查已经排在帧体完整性检查之前**（`decoder.h:44` → `:45`）。这一点现在多了第二个理由：违反它会让 `incomplete` 携带一个未经校验的 `body_len`，读缓冲重新变成无界——即 4.3 引入 `incomplete` 所要消灭的那个 bug 会换条路重建。
- **`in_buf.size() - wire_size` 的无符号下溢不可达**，因为 `:31` 已先返回。且 `gotchas.md` 记载这个减法写法是**有意的**（原为防 32 位平台上 `body_len` 接近 `UINT32_MAX` 时右侧溢出），故 `:45` 的算术**不要改**，只改返回值。附带一条订正：那条防溢出的理由本身已于 7/30 失效——`:44` 把 `body_len` 卡在 65530 以内后，`6 + body_len` 在 32 位上也不可能溢出。写法保留无害，但它现在靠的是顺序，不是自身。

### 4.6 `!msg.is_valid()` 的归类：保持 `error`

`decoder.h:57` 拦下的是**帧结构完全合法、只是业务字段为空**的情形。RFC 9113 的连接错误/流错误判据是「这个错误是否*阻止了帧层继续处理或损坏了连接状态*」——按这条判据，帧体长度已知、游标完全可信，它**不该**是连接级错误；该规范在三处（§4.1、§5.5、§5.1「minimally process and then discard」）都要求对这类帧"推进全部分帧状态，但不向上交付"。

尽管如此，本轮决定**保持 `error`、杀连接**，理由是实现代价与调研初期的估计不符：

- 新增一个 `dropped` 枚举值**不是**"多一个常量"。提交点在 `decoder.h:65-66`，只有 `ok` 走得到；`dropped` 路径下出参逐位未动、`body_len_` 是默认的 0，**调用方算不出 `consumed`**，游标推进直接失效。
- 三条出路各有代价：把 `out_rmp.fh_ = fh` 提前到 JSON 阶段之前，会**打破 D20「失败时出参逐位不变」后置条件**——那是 7/27 codec 异常逸出复盘挣来的硬成果；给 `decode` 加 `out_consumed` 出参，波及 `tests/` 共 28 处调用点的纯机械改动，且分帧状态机落地时该出参注定要删；由核心层自行重解帧头字节则是把线格式知识复制进核心层，最差。

因此本轮定性为**推迟而非解决**：`dropped` 的天然归宿是分帧状态机——届时解码器自持游标、能原生报告 `consumed`，那时它才真的只是一个常量。`codec.md` 与 `tests/test_decoder.cpp:264-273`（D19）记录的"空正文该由解码器当协议错误拒绝，还是放行给上层"这一悬案维持原状。

**连带后果**：本方案落地后 `controller.cpp:18-20` 的 `!rmp.is_valid()` 兜底**变成死代码**——`message_handler_` 只在 `ok` 时被调用，而 `ok` 蕴含 `msg.is_valid()` 已过且帧头两枚举已知。代码保留（`Controller::process` 是公有方法，跨层防御便宜），但 `controller.cpp:16-17` 那句"core.cpp:157 暂未使用 decode 的返回状态，解码失败时一个默认构造的空 `MessagePack` 会到达这里"必须改写——它会在方案落地的瞬间变成假话。

### 4.7 一条 critical conflict：`-Wswitch` 兜底并不存在

`codec.md` 与 `binary_code.h:38-39` 都记着「两个函数有意不写 `default:`，新增枚举值时由 `-Wswitch` 提醒同步扩展」。核实结果：**全仓没有 `-Wall` / `-Wswitch` / `-Werror`**——唯一的编译选项是 `CMakeLists.txt:24` 的 MSVC `/utf-8`，`src/`、`src/server/`、`tests/` 三个 CMakeLists 均未设 `target_compile_options`。GCC 的 `-Wswitch` 仅由 `-Wall` 打开。

后果：给 `io_status.h` 加枚举值后，`to_string` 会**静默**落到 `return "Unknown"`，零诊断。"缺 `default:`"的纪律是真的，编译器提醒是假的。

缓解已列入子任务 S1：手工补 case，**并**在 `tests/test_io_status.cpp` 加逐值断言——该测试在 CI 覆盖内，能把机制补回来。是否统一开启警告选项属于更大的构建改动，本轮未纳入。
