## 1. 编码边界检查（commit 57a8a4c）

### 1.1 背景：m10 联调发现的环境级 OOM

8/6 日志 §9.1「M8+M10 端到端联调」的副产品：`content_bytes = 10^10` 的超长 content 在检查前先分配 27.9~45.8GiB（`make_padded_content` → JSON dump 链），WSL2 VM 级内存耗尽，双进程**无声退出**。根因链条与修复清单见 `knowledge/bugs/2026-08-07-m10-silent-exit.md`（53 分钟前归档，`verified: yes`）。

### 1.2 Encoder 零分配预检（encoder.h）

- `content_.size() > max_message_body_length` 直接 `frame_too_long`，排在 `body_serializer`（任何分配）之前（`encoder.h:81`）。
- 原 `serialized.size()` 检查保留为防 JSON 转义膨胀的后置防线（`encoder.h:87`，注释 `:80` 明确「保留不动」）。
- 与既有「先校验后分配」次序纪律一致（`decoder.h` 1:1 放大比论证、`encoder.h:91-101` resize 次序硬约束）。

### 1.3 客户端护栏（client/main.cpp）

- `kMaxSenderCount = 1'000'000`：m10 count 上限（`main.cpp:68`），杜绝「count 巨大 → 运行时长任意拉长」的自伤。
- `kMaxAccBytes = 1MiB`：入站累积缓冲上限，对齐服务端 `kWriteHighWater` 语义；合法帧最大 65536B，1MiB 是其 16 倍，不误伤正常流量（`main.cpp:69-71`）。
- m10 `content_bytes` 预检（`main.cpp:417-422`）：超限在 `make_padded_content` 之前拒绝，阻断先分配再检查路径。
- 三处 acc 累积点（recv_frames / pump_inbound / run_receiver）全部接入 `kMaxAccBytes` 检查。

### 1.4 E9 回归（test_encoder.cpp:275-301）

`content 70000B → frame_too_long + out_len == 0 + out_buf 哨兵区一字节未动 + body_len_ 不回写`。注释明说「此前该契约零覆盖」——编码侧 frame_too_long 的第一个回归测试。

## 2. core 出队 EPOLLOUT 武装（本次 commit）

### 2.1 问题

出队循环写目标返回 `would_block`（`Connections::flush` 遇 `EAGAIN/EWOULDBLOCK`，`connections.cpp:91`）时无任何分支处理：数据已全部进入目标 `write_buf_`（`Connections::send` 先 insert 后 flush），但目标 fd 的 epoll 掩码仍是纯 `EPOLLIN`（`core.cpp:126-130`），`update_events` 只对当前 fd 调用（`core.h:45`）——目标连接没有事件在途，永远不会自己走到 `update_events`，出站数据静默无限期滞留。

### 2.2 处置：would_block 是背压，不是失败

`would_block` 语义：内核发送缓冲满，连接活着、数据没丢、在 `write_buf_` 里等排空。与 `closed`（EPIPE/ECONNRESET）、`error`（`kWriteHighWater` 1MiB 拒绝入队，数据未进缓冲）的本质区别：**后两者数据不在缓冲里，杀目标不丢已入队数据；前者数据在缓冲里，杀目标 = 丢弃全部滞留数据**。

- 跨 fd：`update_events(to_fd, to_conn)` 挂 `EPOLLOUT`（`core.cpp:253-258`）。目标可写 → `EPOLLOUT` 事件 → `on_writeable()` flush 排空 → `want_write()` 为假 → 掩码重算自动摘除（`core.cpp:294-305`）。LT 空转不成立：`EPOLLOUT` 只在 socket 可写时报告，flush 遇 EAGAIN 即不可写，事件自然停发。
- 自发自收（`to_fd == fd`）：无需处置——`handle_client` 末尾的 `update_events(fd, conn)` 已按 `want_write()` 给当前 fd 挂上 `EPOLLOUT`，进分支杀自己反而误杀。
- 目标 `pending_close_` 已在出队循环 `core.cpp:227` 排除；`EPOLL_CTL_MOD` 对已摘出 fd 返回 ENOENT 无害。

### 2.3 验证（ctest + M8/M9/M10 双进程）

- ctest 10/10 通过（无目标链 core，结构性缺口见 §7.1）。
- 场景 1（基线）：M8 alice 慢读 + M10 bob 发 10×64B → 10/10 转发送达、10/10 回执，发送方存活。
- 场景 2（背压闭环）：M8 1s tick 慢消费 + M10 突发 200×4096B（800KB）→ M8 收到 **200/200** 帧（改前 would_block 静默滞留，M8 只能收到内核缓冲容量以内的部分）。
- 场景 3（顶爆归因）：M9 停读 + M10 发 3000×4096B（12MB）→ 服务端日志 `[core] send to fd 5 failed (Error); closing target, sender fd 6 unaffected`——would_block 武装不误杀，累积越过 1MiB 高水位后 `error` 归因杀**目标**，发送方收满 3000 条回执（尾部 status=1 为 alice 下线后的 fail）且存活。
- 首轮场景 3（300×4KB = 1.2MB）未触发目标路径：WSL2 TCP 接收缓冲 autotune 吸收了全部字节，flush 从未 EAGAIN。测试方法学记录：**要触发 would_block，发送量必须超过内核接收缓冲**（12MB 才顶爆）。

## 6. 审查发现的问题

### 6.1 core 仍无测试目标链

`tests/CMakeLists.txt` 只链 controller.cpp，核心层消息路径的回归只能靠 M8/M9/M10 手工双进程（gotchas 第 19 条）。本次武装无自动化防线，场景 2/3 的验证脚本未沉淀为可重复测试。

### 6.2 would_block 路径无日志

武装分支静默（continue），观测只能靠行为（送达 vs 滞留）。「调试观测点缺失」TODO 项（controller 普通消息路径）仍未消费；core 出队循环的 would_block 命中次数如要观测，需另行设计计数/日志。

### 6.3 M9 无法自观测被杀

M9 停读变体不 recv 也不 poll，连接被服务端杀死时自身无感知，hold 到期一律打印「still connected」。断言依赖服务端日志侧证。

### 6.4 WSL2 内核缓冲吸收量不可控

场景 3 首轮 1.2MB 全被内核缓冲吸收（未触发 EAGAIN）。发送量必须按「内核缓冲 + 1MiB 高水位」估算，12MB 才稳定顶爆——验证脚本的触发条件对环境敏感。
