# 2026-07-27 - 解码器实现与编解码修正

> 解码器不再是一具骨架——帧头校验、枚举值域检查、JSON 反序列化全线对齐。

## 概览

解码器 `Decoder::decode()` 从骨架补全为完整实现；编码器职责修正（`no_padding_size` 迁移为 `FrameHeader::wire_size`、错误返回语义收紧）；测试体系从散装 `assert` 重构为三类断言正交覆盖（出站黄金字节、入站黄金字节、往返组合）。

## 解码器实现（fda047a, d7690a6）

此前 `decoder.h` 只有一行空壳 `decode()`（参见 2026-07-23 日志 §Decoder 骨架）。本次将完整分帧与反序列化逻辑填入，流程如下：

1. **尺寸守卫**：`in_buf.size() < FrameHeader::wire_size` → 直接 `error`；
2. **枚举值域校验**：`is_known_opcode(raw_opcode)` 与 `is_known_status(raw_status)` 先于 `static_cast` 执行——线上未知字节值一律按协议错误拒绝；
3. **体长提取**：`std::memcpy` + `ntohl` 解析大端 `body_len_`；
4. **载荷完整性**：`in_buf.size() - FrameHeader::wire_size < body_len` → `error`，防止越界读；
5. **JSON 解析**：`nlohmann::json::parse(..., allow_exceptions=false)`，双重防卫——先 `j.is_discarded()` 捕获格式错误，再 `j.is_object()` 拒绝非对象 JSON（`"[1,2,3]"` 与 `null` 均会被 `parse` 放过，必须显式过滤）；
6. **消息合法性**：`j.get<types::RequestMsg>()` → `msg.is_valid()`，字段缺失或类型错误在此截获；
7. **原子交付**：`out_rmp.fh_` 与 `out_rmp.request_msg_` 同时赋值——失败路径返回 `error` 时 `out_rmp` 一字节未动，调用方不会读到半成品。

### 枚举值域校验

`binary_code.h` 新增两个 `constexpr` 校验函数（`is_known_opcode` / `is_known_status`）。它们不写 `default:` 分支——新增枚举值时 `-Wswitch` 会提醒此处需同步扩展，避免静默放行未知值。

```cpp
constexpr bool is_known_opcode(std::uint8_t raw) noexcept {
    switch (static_cast<Opcode>(raw)) {
        case Opcode::ack:
        case Opcode::request:
        case Opcode::response: return true;
        case Opcode::_init_:   return false;
    }
    return false;   // 不在枚举列表中的线上字节
}
```

## 编码器修正（fda047a）

### `no_padding_size` → `FrameHeader::wire_size`

此前 `Encoder` 持有静态常量 `no_padding_size = 6`，用于指示帧头在线尺寸。该值实为 `FrameHeader` 的结构属性——帧头几个字段的 `sizeof` 之和——而非编码器的决策。本次将其提升为 `FrameHeader::wire_size`，编译期由三个字段类型推导：

```cpp
static constexpr std::size_t wire_size =
    sizeof(decltype(FrameHeader::opcode_))
    + sizeof(decltype(FrameHeader::status_))
    + sizeof(decltype(FrameHeader::body_len_));
```

`core.cpp` 中调用方同步替换：`Encoder::no_padding_size` → `FrameHeader::wire_size`。`docs/architecture.md` 中帧头尺寸从"8 字节"同步修正为"6 字节"（删除错误记载的 `reserved` 字段）。

### 错误返回语义收紧

`header_encoder` 此前返回 `IoStatus` 并在 `body_len_ == 0` 时返回 `error`——这不对：长度为 0 的消息（如纯 ACK）是合法帧。修正：`header_encoder` 改为 `void` 返回，仅执行写入；`encode()` 的 `noexcept` 保证通过 `try/catch (...)` 兜底 JSON 序列化的 `std::bad_alloc` 与 `type_error` 异常。

### 输出长度显式传递

`encode()` 新增 `uint32_t& out_len` 输出参数，调用方不再需要自行计算 `max_message_body_length + wire_size`——编码器在成功路径返回实际字节数，失败时 `out_len = 0`。

### const 正确性

`message.h` 中 `RequestMsg::is_valid()` 与 `ResponseMsg::is_valid()` 补上 `const` 限定。`message_pack.h` 中三参数构造函数改为按值传参（`types::RequestMsg` 而非 `const&`），配合 `std::move` 语义。

## 测试体系重构（d7690a6）

测试从散装 `assert` 迁移为三类正交断言，每类钉死一条不重叠的契约边：

### 公共设施（`tests/test_support.h`）

- **`CHECK(cond)`**：不受 `NDEBUG` 影响的断言宏，Release 构建下同样生效，失败时打印文件/行号；
- **`make_frame(opcode, status, declared_len, body)`**：手工构帧——大端长度由显式移位写出，刻意不用 `htonl`、不 `#include <netinet/in.h>`、不触碰 `Encoder`——防止黄金向量与被测代码共享同一个字节序 bug；
- **`make_frame(opcode, status, body)`**：便捷重载，`declared_len` 取 `body.size()`；
- **`body_of(buf, off, n)`** / **`hex_dump(buf, n)`**：测试辅助工具。

### 断言类别 (a)：出站黄金字节（`test_encoder.cpp`）

`encode` 的输出与手工推导的黄金字节逐字节比对。**不调用 `decode`**——因此 `htonl`/`ntohl` 若同时写错也无法互相掩盖。覆盖：

- E1-E3: ASCII / 多字节长度 / UTF-8 CJK 的帧头+帧体完整逐字节比对
- E4: `body_len_` 副作用校验（编码后 `rmp.fh_.body_len_` 被正确回填）
- E5: 不写到缓冲区边界外
- E6: 非法 UTF-8 输入被 JSON `dump()` 的 `error_handler_t::strict` 截获
- E7: 空字符串的最小帧
- E8: `encode()` 是 `noexcept`

### 断言类别 (b)：入站黄金字节（`test_decoder.cpp`）

手工构造的黄金字节 → `decode` → 断言字段值。**绝不调用 `Encoder`**——即使编码器与解码器共享同一个字节序 bug，本文件也会红。覆盖 20 个用例，包括：

- D1-D3: 手工帧的正确解码（ASCII / 多字节长度 / UTF-8 CJK）
- D4-D5: 超大/精确尺寸缓冲区的容错
- D6-D8: 过短缓冲、截断体、荒谬声明长度的拒绝
- D9-D12: 未知/`_init_` 枚举值的拒绝
- D13: 全部已知 opcode 可正确解码
- D14-D17: 畸形 JSON / 缺失字段 / 类型不匹配 / 非对象 JSON / null 的拒绝
- D18: 空 `content` 的拒绝
- D19: 失败路径下 `out_rmp` 不被污染
- D20-D21: `decode()` 是 `noexcept`；`RequestMessagePack` move 赋值是 `nothrow`

### 断言类别 (c)：往返（`test_roundtrip.cpp`）

`encode` → `decode` 往返。**只能**证明 encode 与 decode 彼此一致，不能证明任何一方在线格式上是对的。本文件负责的是可组合性：完整链路上字段不丢、不错位、不被 1024 字节缓冲区尾部零字节干扰。覆盖：

- R1: 完整 1024 字节缓冲区直接喂 `decode`（修复前此处返回 `error`——缓冲区尺寸被当成帧长）
- R2: 多字节长度消息
- R3: CJK 消息
- R4: opcode 与 status 字段不互换（两者都是 1 字节相邻字段，取值刻意不等）
- R5: 裁剪到 `out_len` 精确尺寸的缓冲区同样成立

### 构建系统

`CMakeLists.txt`：默认构建类型设为 `Debug`（防止未配置时以无优化/无符号的奇怪状态构建）。`tests/CMakeLists.txt` 新增 `test_decoder` 与 `test_roundtrip` 目标。

## 下一步

1. **帧校验机制**：当前编码与解码均无完整性校验——帧头不含 magic number / checksum / 帧尾定界符。TCP 字节流下，`body_len_` 字段本身若被损坏或错位，解码器将读取错误长度的帧体并产生不可预测的反序列化结果。计划方案：帧头增加 1 字节 magic（如 `0xCE`），帧尾增加 2 字节 CRC16（覆盖帧头+帧体），使解码器能够在三个层面判定帧边界——magic 定位帧头、`body_len_` 定界帧尾、CRC 验证完整性。（继承自 2026-07-23 日志，尚未实施）

2. **零拷贝编码路径**：当前编码器写入调用方提供的 `std::vector<std::byte>`，再经 `conn.send()` 拷贝进 `write_buf_`。若编码器直接写入 `Connections::write_buf_` 尾部，可省去一次全帧拷贝。前提是校验机制先行到位——因为写入后不再有"回看并修正"的机会。（继承自 2026-07-23 日志，尚未实施）

3. **分帧状态机**：当前解码器假定调用方已通过外部机制（如 `epoll` + 缓冲累积）将完整帧切出。TCP 粘包/半包问题尚未在解码器层解决——需要内置状态机，支持从 `read_buf_` 中增量消费字节、在帧头不完整时等待更多数据、在帧体不完整时暂存已接收部分。"分帧逻辑应当在 decoder 之外就完成了"（`decoder.h:25`）的注释意味着分帧是连接层的职责——这一点需要在架构文档与实现之间对齐。

4. **性能与覆盖率**：当前测试以正确性为主，未涉及边界性能（碎片化输入、百万消息压测）。后续可引入基准测试框架，与编解码器内部缓冲复用改造配套落地。
